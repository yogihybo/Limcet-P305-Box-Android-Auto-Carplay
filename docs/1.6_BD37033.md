# 1.6 Audio Codec IC (BD37033)

Background doc for [README §1.0 Hardware](../README.md#10-hardware) — Audio IC row.

Reverse-engineering notes for the `Sound_BD37033` class found in
`/home/osboxes/Downloads/cstech-ip17-rootfs/rootfs/usr/lib/libMsnSound.so`.

All information below was extracted directly from ARM disassembly
(`arm-linux-gnueabihf-objdump -d`) of the stripped-but-symbol-bearing
shared object. Raw addresses/opcodes are included as evidence. Register
**numbers** and bit positions are exact (read straight from the machine
code); register **semantic names** (e.g. "mute bit," "master attenuator")
are inferred from behavior and typical Rohm BD37033 register-map
conventions and should be cross-checked against the official datasheet
before being relied on for reflashing/tampering purposes.

## 2. Bus wiring

### GPIO — enable/reset line, and why it may be silently failing

```
a5a4: bl GPIOOperater::GPIOOperater(unsigned short pin=34)   ; r1 = 34  -> GPIO #34
a5d8: bl GPIOOperater::setDir("out")                          ; string @ 0x0000d994 = "out"
a5e0: mov r1, #0
a5e4: bl GPIOOperater::setValue(0)                            ; GPIO34 driven LOW at construction
```

- **GPIO34**, configured as **output**, driven **LOW once** at object construction.
- It is never toggled again anywhere in `Sound_BD37033` — this is a one-shot
  hardware line (likely reset / power-enable / mute-select) asserted at
  startup; all subsequent control is via I2C.
- The `GPIOOperater` object is embedded (placement-constructed) inside the
  `Sound_BD37033` instance, not heap-allocated separately.
- `GPIOOperater(pin=34)` maps 1:1 to Linux sysfs `/sys/class/gpio/gpio34/*`
  — confirmed by disassembling `GPIOOperater`'s implementation in
  `libMsnCommons.so` (constructor calls `gpio_export(34)` with the pin
  number passed through unmodified). This is the **same GPIO number**
  `libCanBus.so` references via literal `echo 0/1 >
  /sys/class/gpio/gpio34/value` shell commands (see
  [`docs/1.2_CANBUS.md`](1.2_CANBUS.md) / [`hardware/BOARD_ANALYSIS.md`](../hardware/BOARD_ANALYSIS.md))
  — on this unit `CanType=0` so that path is dormant, but it confirms the
  numbering scheme and that GPIO34 is a generic, board-variant-dependent
  line reused across the shared `libMsnCommons.so`/`GPIOOperater` codebase.

#### Traced: `gpio_export()` / `gpio_set_dir()` / `gpio_set_value()` (in `libMsnCommons.so`)

All three are small local helpers in `libMsnCommons.so` (not provided by
any lower-level lib), following an identical pattern —
`open("/sys/class/gpio/...", O_WRONLY)`, `snprintf`+`write()` the value,
`close()`:

```
gpio_export(pin):
    fd = open("/sys/class/gpio/export", O_WRONLY)
    if (fd < 0) { printf("Failed export GPIO-%d", pin); return fd; }
    write(fd, "<pin>", ...);   // <-- return value of write() NOT checked
    close(fd);
    return 0;                  // <-- ALWAYS 0 once open() succeeded

gpio_set_dir(pin, "out"/"in"):
    fd = open("/sys/class/gpio/gpio<pin>/direction", O_WRONLY)
    if (fd < 0) { printf("Failed set GPIO-%d direction", pin); return fd; }
    write(fd, dir_str, ...);   // <-- return value of write() NOT checked
    close(fd);
    return 0;

gpio_set_value(pin, val):
    fd = open("/sys/class/gpio/gpio<pin>/value", O_WRONLY)
    if (fd < 0) { printf("Failed set GPIO-%d value", pin); return fd; }
    write(fd, val ? "1" : "0", 2);   // <-- return value of write() NOT checked
    close(fd);
    return 0;
```

`GPIOOperater::setDir()`/`setValue()` are pure tail calls into
`gpio_set_dir()`/`gpio_set_value()` (`b`, not `bl` — the callee's return
value becomes the caller's return value untouched) **gated only on
`getIONum() != 0`** (i.e. whether `gpio_export()` "succeeded"):

```
GPIOOperater::setDir(dir):
    if (getIONum() == 0) return -1;
    return gpio_set_dir(getIONum(), dir);   // tail call, b not bl
```

**Two concrete, verified failure modes with zero error propagation to
`Sound_BD37033`:**

1. **`write()`'s return value is discarded in all three helpers.** If the
   `open()` succeeds but the `write()` fails — e.g. `EINVAL` because
   pin 34 isn't muxed to plain-GPIO function in the kernel/device-tree's
   pinctrl setup — none of `gpio_export()`/`gpio_set_dir()`/`gpio_set_value()`
   notice or report it. They all return `0` (success) regardless.
2. **Even the `open()`-failure path (which *is* detected and `printf`'d)
   is never checked by the caller.** `Sound_BD37033`'s constructor calls
   `setDir("out")` then `setValue(0)` back-to-back and never inspects
   either return value (no `cmp`/branch on `r0` after either `bl` at
   `a5d8`/`a5e4`). A failed `open()` on `/sys/class/gpio/gpio34/direction`
   (e.g. `ENOENT` from the well-known sysfs-GPIO export race — the
   `gpio34` subdirectory may not exist yet in the instant right after
   `gpio_export()`'s `write()` returns, since directory creation isn't
   synchronous with the export write) would print `"Failed set GPIO-34
   direction"` to stdout and then be **completely ignored** by the sound
   driver, which proceeds as if nothing happened.

**Why this matters for "no sound output":** either failure mode leaves
GPIO34 in whatever state it powered on in — never actually driven LOW
(or never actually reaching the BD37033, if pinmux is the problem) —
with **no crash, no log line reaching any file, and no visible symptom
inside `MsnCoreApp` at all**. This project has an existing history of
ARK1668 pinmux issues elsewhere (LCD pinmux, clock gating — see the
Limcet P306 board reconstruction commits), and this repo's own pin dumps
already flag pin 34 specifically as ambiguous:
`docs/logs/pindump stock annotated.txt` records `pin 34 (reg=0x1dc
off=8 mask=0x3): PVAL=0 -> no named pinctrl group (plain GPIO or
undocumented function)` — i.e. pin 34 was never observed with a named
pinctrl group on the stock dump either, consistent with (but not proof
of) a pin whose GPIO-vs-peripheral-function muxing isn't nailed down.

**Concrete ways to test this on real hardware, no rebuild required:**

- `ls /sys/class/gpio/` right after launching `MsnCoreApp` — confirm
  `gpio34` actually exists (rules out the `open()`-fails-silently-ignored
  path if present).
- `cat /sys/class/gpio/gpio34/direction` and
  `cat /sys/class/gpio/gpio34/value` — confirm they read back `out` / `0`
  as the driver intends. If `gpio34` exists but reads back something
  other than `out`/`0`, the `write()`s are the ones failing silently
  (pinmux-adjacent), not the `open()`s.
- If `gpio34` genuinely reflects `out`/`0` correctly and there's still no
  sound, GPIO34 is very likely fine and the fault lies elsewhere (I2C
  writes, downstream analog path) — this test cleanly rules the GPIO
  path in or out.
- As a one-off manual test (no code changes): `echo 34 >
  /sys/class/gpio/export` (if not already exported), `echo out >
  /sys/class/gpio/gpio34/direction`, then try both `echo 0` and `echo 1
  > /sys/class/gpio/gpio34/value` while listening — the doc's "LOW enables
  the chip" assumption is inferred from typical BD37033-family STBY pin
  conventions, not confirmed against a datasheet, so it's worth checking
  the opposite polarity too.

### I2C

```
aaf4: mov r1, #2      ; I2C bus number
aaf8: mov r2, #0x80    ; I2C device address (8-bit form)
ab00: bl I2COperator::I2COperator(unsigned char bus, unsigned char addr)
ab04: str r4, [r6, #0x58]   ; I2COperator* saved at object+0x58, used by every register write
```

- **I2C bus 2**
- **Device address `0x80`** (8-bit write address) → **7-bit address `0x40`**,
  matching the real BD37033's factory-default slave address.
- The stored `I2COperator*` at object offset `+0x58` is loaded by every
  `bd37033_*` method before calling `I2COperator::writeData(...)`.

## 3. Object memory layout (bytes, `Sound_BD37033` instance)

| Offset | Contents |
|---|---|
| `0x0c – 0x23` | Embedded `GPIOOperater` member (GPIO34) |
| `0x24` | Qt-related state (128-bit zero store, likely timer/QVariant) |
| `0x38 – 0x4b` | 20-byte **register cache**, mirrors chip sub-addresses `0x01–0x14` |
| `0x58` | `I2COperator*` pointer (bus 2, addr 0x40) |
| `0x59-ish (offset 0x59/0x5c region)` | New object allocated in ctor (`new` of 12 bytes) — the `I2COperator` instance itself |

Cache-byte reuse observed:
- `object+0x3C` is shared between `bd37033_set_mute()` and
  `bd37033_set_input_gain()` — both read/modify/write the **same** cached
  byte, which is then sent as **register 6**. This is consistent with a
  single physical register combining a mute bit and a gain field.
- `object+0x3A` → register 3 cache (mixing setup).
- `object+0x3B` → register 5 cache (input channel select).
- `object+0x3D` → register 0x20 cache (master volume/attenuator).

Resulting **single burst write**, sub-address `0x01`, 20 bytes:

```
Sub-addr:  01   02   03   04   05   06   07   08   09   0A   0B   0C   0D   0E   0F   10   11   12   13   14
```

This is the exact power-up configuration table baked into the driver:
mute/gain reg (06) defaults to `0xFF` region alongside several attenuators
maxed at `0xFF`, three input-gain-adjacent registers preset to `0x80`, and
a couple of channel regs preset to `0x00`.

## 5. `bd37033_set_mute(int on)` @ `0x99dc` — register 6, bit 7

```asm
000099dc <Sound_BD37033::bd37033_set_mute(int)>:
    99dc: cmp   r1, #1
    99e0: push  {lr}
    99e4: sub   sp, sp, #12
    99e8: ldrb  r3, [r0, #60]        ; cached reg-6 byte (+0x3C)
    99ec: beq   9a1c
    99f0: cmp   r1, #0
    99f4: andeq r3, r3, #0x7f        ; on==0  -> clear bit7 (unmute)
    99f8: strb  r3, [sp, #7]
    99fc: strb  r3, [r0, #60]        ; update cache
    9a00: mov   r1, #6               ; reg 6
    9a04: add   r2, sp, #7           ; data ptr
    9a08: mov   r3, #1               ; len 1
    9a0c: ldr   r0, [r0, #88]        ; I2COperator*
    9a10: bl    I2COperator::writeData(6, &byte, 1)
    9a14: add   sp, sp, #12
    9a18: pop   {pc}
    9a1c: orr   r3, r3, #0x80        ; on==1  -> set bit7 (mute)
    9a20: strb  r3, [sp, #7]
    9a24: b     99fc
```

- **Register 6, bit 7** = mute flag. `on!=0` sets it, `on==0` clears it.
  Read-modify-write against the cached byte, so the gain field (bits 0-6,
  see §7) is preserved across mute toggles.

## 6. `bd37033_select_input_channel(uchar ch)` @ `0x9a28` — register 5

```asm
00009a28 <Sound_BD37033::bd37033_select_input_channel(uchar)>:
    9a28: push {r4,r5,r6,r7,lr}
    9a2c: cmp  r1, #31
    9a30: sub  sp, sp, #12
    9a34: ldrb r2, [r0, #59]        ; cached reg-5 byte (+0x3B)
    9a38: mov  r4, r0
    9a3c: mov  r5, r1               ; r5 = ch
    9a40: ldrb r7, [r0, #60]        ; cached reg-6 byte (+0x3C), saved mute state
    9a44: strb r2, [sp, #7]
    9a48: bhi  9a74                 ; ch > 31 -> no-op / return
    9a4c: mov  r6, #1
    9a50: movw ip, #3919            ; 0x0F4F -- validity bitmask for ch 0..15
    9a54: lsl  lr, r6, r1           ; lr = 1 << ch
    9a58: and  ip, ip, lr
    9a5c: cmp  ip, #0
    9a60: bne  9a7c                 ; ch is in the "always-mute-first" set
    9a64: cmp  lr, #0
    9a68: blt  9adc                 ; ch == 31 (sign bit) special case
    9a6c: tst  lr, #0x8000          ; ch == 15 special case
    9a70: bne  9ab4
    9a74: add  sp, sp, #12
    9a78: pop  {r4,r5,r6,r7,pc}     ; (fallthrough no-op path)

    9a7c: mov  r1, r6               ; r1 = 1  -> mute ON first
    9a80: bl   bd37033_set_mute(1)
    9a84: add  r2, sp, #8
    9a88: mov  r3, r6               ; len 1
    9a8c: strb r5, [r2, #-1]!       ; data byte = ch
    9a90: strb r5, [r4, #59]        ; update cached reg-5
    9a94: ldr  r0, [r4, #88]
    9a98: mov  r1, #5               ; reg 5
    9a9c: bl   I2COperator::writeData(5, &ch, 1)
    9aa0: mov  r0, r4
    9aa4: lsr  r1, r7, #7           ; r1 = previous mute bit (restore)
    9aa8: bl   bd37033_set_mute(prev)
    9aac: add  sp, sp, #12
    9ab0: pop  {r4,r5,r6,r7,pc}

    9ab4: and  ip, r2, #0x7f        ; (ch==15 path) clear bit7 of cached reg5
    9ab8: add  r2, sp, #8
    9abc: strb ip, [r4, #59]
    9ac0: ldr  r0, [r4, #88]
    9ac4: mov  r3, r6
    9ac8: strb ip, [r2, #-1]!
    9acc: mov  r1, #5
    9ad0: bl   I2COperator::writeData(5, &val, 1)
    9ad4: add  sp, sp, #12
    9ad8: pop  {r4,r5,r6,r7,pc}

    9adc: orr  ip, r2, #0x80        ; (ch==31 path) set bit7 of cached reg5
    9ae0: b    9ab8
```

- **Register 5** = input channel select (channel index `0..31`, validated
  against a bitmask table `0x0F4F` for the low 16 channels, plus two
  special-cased channels 15 and 31 that instead manipulate bit 7 of the
  cached reg-5 byte directly).
- The function **mutes before** writing the new channel and **restores
  the previous mute state after** — standard pop/click suppression during
  input switching. Confirms register 6's mute bit (§5) is shared logic.

## 7. `bd37033_set_input_gain(uchar gain)` @ `0x9bbc` — register 6, bits 0–6

```asm
00009bbc <Sound_BD37033::bd37033_set_input_gain(uchar)>:
    9bbc: push  {lr}
    9bc0: ldrsb r3, [r0, #60]       ; signed read of cached reg-6 byte
    9bc4: cmp   r1, #20
    9bc8: movcs r1, #20             ; clamp gain to max 20
    9bcc: sub   sp, sp, #12
    9bd0: cmp   r3, #0
    9bd4: orrlt r1, r1, #0x80       ; if cached byte was "negative" (bit7 set) -> re-set mute bit
    9bd8: add   r2, sp, #8
    9bdc: strb  r1, [r0, #60]       ; update cache
    9be0: strb  r1, [r2, #-1]!
    9be4: mov   r3, #1
    9be8: mov   r1, #6              ; reg 6
    9bec: ldr   r0, [r0, #88]
    9bf0: bl    I2COperator::writeData(6, &val, 1)
    9bf4: add   sp, sp, #12
    9bf8: pop   {pc}
```

- **Register 6, bits 0–6** = input gain, range **0–20** (clamped, likely
  0–20 dB in 1 dB steps — typical for this chip family). Shares the same
  physical register/cache byte as the mute bit (bit 7), and preserves the
  existing mute state while updating gain.

## 8. `bd37033_mixing_setup(int slot, uchar val)` @ `0x9ae4` — register 3

```asm
00009ae4 <Sound_BD37033::bd37033_mixing_setup(int,uchar)>:
    9ae4: push {lr}
    9ae8: sub  sp, sp, #12
    9aec: ldrb r3, [r0, #58]        ; cached reg-3 byte (+0x3A)
    9af0: cmp  r1, #3
    9af4: addls pc, pc, r1, lsl #2  ; jump table, slot 0..3
    9af8: b    9b18                 ; slot 0 (also default/fallthrough)
    9afc: b    9b50                 ; slot 1
    9b00: b    9b64                 ; slot 2
    9b04: b    9b3c                 ; slot 3
    9b08: b    9b0c

    9b0c: and  r3, r3, #0x3f
        ; slot 0: bits[7:6] = val (2-bit field)
        orr  r3, r3, r2, lsl #6
    9b3c: bic  r1, r3, #0x18
        ; slot 3: bits[4:3] = val (2-bit field)
        orr  r3, r1, r2, lsl #3
    9b50: bic  r1, r3, #0x02
        ; slot 1: bit[1] = val (1-bit field)
        orr  r3, r1, r2, lsl #1
    9b64: bic  r1, r3, #0x04
        ; slot 2: bit[2] = val (1-bit field)
        orr  r3, r1, r2, lsl #2

    9b18: strb r3, [sp, #7]
    9b1c: strb r3, [r0, #58]        ; update cache
    9b20: mov  r1, #3               ; reg 3
    9b24: add  r2, sp, #7
    9b28: mov  r3, #1
    9b2c: ldr  r0, [r0, #88]
    9b30: bl   I2COperator::writeData(3, &val, 1)
    9b34: add  sp, sp, #12
    9b38: pop  {pc}
```

- **Register 3** = a mixing/routing control register, packed as a
  bitfield selected by `slot` (0–3):
  - slot 0 → bits `[7:6]` (2-bit field)
  - slot 1 → bit `1` (1-bit field)
  - slot 2 → bit `2` (1-bit field)
  - slot 3 → bits `[4:3]` (2-bit field)

## 9. `bd37033_set_volume_gain(uchar v)` @ `0x9b78` — register 0x20 (32)

```asm
00009b78 <Sound_BD37033::bd37033_set_volume_gain(uchar)>:
    9b78: tst  r1, #0x80
    9b7c: push {lr}
    9b80: sub  sp, sp, #12
    9b84: bne  9bb4                 ; bit7 set -> use raw value
    9b88: mvn  r3, #127             ; r3 = 0x80 (default byte)
    9b8c: mov  r1, #0x80
    9b90: strb r3, [sp, #7]
    9b94: strb r1, [r0, #61]        ; update cached reg (+0x3D)
    9b98: add  r2, sp, #7
    9b9c: mov  r1, #32              ; reg 0x20
    9ba0: mov  r3, #1
    9ba4: ldr  r0, [r0, #88]
    9ba8: bl   I2COperator::writeData(0x20, &byte, 1)
    9bac: add  sp, sp, #12
    9bb0: pop  {pc}
    9bb4: strb r1, [sp, #7]         ; bit7 set -> write v verbatim
    9bb8: b    9b94
```

- **Register 0x20 (32)** = master volume / attenuator register, in a
  separate sub-address bank from registers 1–20. If the caller's byte has
  bit 7 clear, the driver silently forces `0x80` instead; otherwise the
  raw byte (which always carries bit 7 set, per §10's curve) is written.

## 10. `setVolume(uchar level, bool flag)` @ `0x9de0` — volume curve → §9

**Corrected 2026-07-16** — the original writeup below had this backwards:
it stated the curve was computed directly on `level`, when it's actually
computed on `32 - level`. That inverts both the endpoint values and which
half of the range gets the plain-linear vs. curved treatment. Re-derived
below by hand-tracing every register against the live disassembly
(`arm-linux-gnueabihf-objdump -C -d` against
`/home/osboxes/Downloads/cstech-ip17-rootfs/rootfs/usr/lib/libMsnSound.so`).

Full disassembly (`r1` = `level`, `r2` = `flag`, reused mid-function as a
scratch register once its boolean value has been consumed):

```asm
00009de0 <Sound_BD37033::setVolume(unsigned char, bool)>:
    9de0: cmp  r1, #32
    9de4: bls  9e3c                  ; level <= 32 -> 9e3c (the normal path)
    9de8: cmp  r2, #0                ; level > 32 (invalid/clamped) -- check flag
    9dec: bne  9e88                  ; flag != 0 -> force gain 0x80, cache[+0x10]=32
    9df0: ldrb r1, [r0, #16]         ; flag == 0 -> reload r1 from cache[+0x10] (last level)
    9df4: cmp  r2, #0                ; (r2 here is whatever fell through, effectively 0 on this path)
    9df8: strb r1, [r0, #16]
    9dfc: beq  9e58                  ; -> gain = 0x80
    9e00: cmp  r2, #32
    9e04: beq  9e60                  ; -> gain = 0xFF
    9e08: add  r3, r2, #128          ; r3 = r2 + 128        (r2 = "32 - level" on the normal path)
    9e0c: cmp  r2, #16
    9e10: vmov s15, r3
    9e14: sub  sp, sp, #8
    9e18: vcvt.f32.s32 s13, s15      ; s13 = float(r2+128)
    9e1c: bhi  9e68                  ; r2 > 16 -> curved branch
    9e20: vldr s15, [pc, #112]       ; = 0.0 (constant pool)
    9e24: vadd.f32 s15, s13, s15     ; s15 = s13 + 0 (no-op on this path)
    9e28: vcvt.u32.f32 s15, s15      ; round to uint
    9e2c: vstr s15, [sp, #4]
    9e30: ldrb r1, [sp, #4]          ; low byte = gain
    9e34: add  sp, sp, #8
    9e38: b    bd37033_set_volume_gain(r1)   ; tail call
    9e3c: cmp  r2, #0                ; original flag test, consumed before r2 is overwritten below
    9e40: rsb  r2, r1, #32           ; r2 = 32 - level   <-- the actual formula input
    9e44: uxtb r2, r2
    9e48: beq  9df0                  ; flag == 0 -> join the shared block above
    9e4c: cmp  r2, #0                ; flag != 0: is (32-level)==0, i.e. level==32?
    9e50: strb r1, [r0, #16]         ; flag != 0: always cache the current level at +0x10
    9e54: bne  9e00                  ; level != 32 -> rejoin the SAME curve as flag==0
    9e58: mov  r1, #128              ; 0x80
    9e5c: b    bd37033_set_volume_gain(r1)   ; tail call
    9e60: mov  r1, #255              ; 0xFF
    9e64: b    bd37033_set_volume_gain(r1)   ; tail call
    9e68: sub  r3, r2, #16
    9e6c: vmov.f32 s15, #10.0
    9e70: vmov  s14, r3
    9e74: vmov.f32 s12, #16.0
    9e78: vcvt.f32.s32 s14, s14
    9e7c: vdiv.f32 s14, s14, s15     ; (r2-16)/10.0
    9e80: vmul.f32 s15, s14, s12     ; * 16.0
    9e84: b    9e24                  ; -> s15 added to s13, rounded, tail-called (see above)
    9e88: mov  r3, #32               ; level > 32 (invalid), flag != 0
    9e8c: mov  r1, #128
    9e90: strb r3, [r0, #16]         ; cache[+0x10] = 32
    9e94: b    9e64                  ; -> gain = 0xFF (note: NOT 0x80, despite r1=128 being set above — r1
                                      ;    is overwritten by the b-9e64 target's own "mov r1,#255")
```

Corrected truth table, in terms of the actual UI `level` parameter (`X = 32 - level` is the internal value the formula runs on):

```
level == 32            -> gain = 0x80  (128)
level == 0              -> gain = 0xFF  (255)
16 <= level < 32        -> gain = 160 - level                              (0x90 down to 0x81)
0  <  level < 16        -> gain = round( (32 - level + 128)
                                          + ((32 - level - 16) / 10.0) * 16.0 )
                                = round( 185.6 - 2.6 * level )             (~0xB7 down towards ~0x90)
level > 32, flag==false -> gain = 0x80  (clamped)
level > 32, flag==true  -> gain = 0xFF  (clamped; also force-sets cache[+0x10] = 32)
```

So the curve is a **descending** gain byte as `level` rises from 0 to 32
(`0xFF` at silence/min-UI-level down to `0x80` at max-UI-level) — the
opposite slope and opposite endpoint mapping from what this section
previously claimed. It's also **not symmetric around a `level<=16` /
`level>16` split** as previously stated: the plain linear segment covers
the *upper* half of the UI range (`level` from 16 to 32), and the curved
VFP segment covers the *lower* half (`level` from 0 to 16) — exactly
mirrored from the original writeup.

**`flag` does not force `gain = 0x80` in general.** Its only effects are:
(1) it always writes the current `level` into the cache byte at
`object+0x10` (this looks like "last commanded level," read back by
`Sound_BD37033::timerEvent()`'s progressive-volume-ramp logic — see
`startVolumeProgressive()`/`timerEvent()` a few functions later in the
same file), and (2) for `level==32` specifically, both `flag==true` and
`flag==false` land on the same `gain=0x80` result anyway — which is
almost certainly why the original analysis mistook that one coincidental
case for "flag forces 0x80" in general. For every other `level`, `flag`
being true or false produces the *identical* gain via the same shared
curve code (`9e00` onward); only the cache side-effect differs.

## 11. `bd37033_set_fader_mixing_gain(uchar id, uchar gain)` @ `0x9d60`

```asm
00009d60 <Sound_BD37033::bd37033_set_fader_mixing_gain(uchar,uchar)>:
    9d60: push {r4,r5,r6,lr}
    9d64: mov  r4, r2               ; r4 = gain
    9d68: sub  sp, sp, #8
    9d6c: mov  r5, r0
    9d70: mov  r6, r1               ; r6 = id
    9d74: bl   get_data_addr(id)    ; r0 = pointer into register cache for this channel
    9d78: cmp  r4, #255
    9d7c: beq  9dd0                 ; gain==0xFF -> mute (write 0xFF)
    9d80: cmp  r4, #0x80
    9d84: bhi  9db8                 ; gain>0x80  -> clamp to 0xCF
    9d88: cmp  r4, #0x70
    9d8c: movls r4, #0x71           ; gain<=0x70 -> clamp to 0x71
    9d90: mov  r3, r4
    9d94: strb r4, [sp, #7]
    9d98: strb r3, [r0]             ; update cache at addr returned by get_data_addr()
    9d9c: mov  r1, r6               ; reg = id  (register number == channel id)
    9da0: ldr  r0, [r5, #88]
    9da4: add  r2, sp, #7
    9da8: mov  r3, #1
    9dac: bl   I2COperator::writeData(id, &byte, 1)
    9db0: add  sp, sp, #8
    9db4: pop  {r4,r5,r6,pc}

    9db8: cmp  r4, #0xcf
    9dbc: movcs r4, #0xcf
    9dc0: uxtb r4, r4
    9dc4: mov  r3, r4
    9dc8: strb r4, [sp, #7]
    9dcc: b    9d98                 ; (clamp-to-0xCF path -- NOT 9d90; re-stores directly then
                                     ; jumps straight to the cache-update + I2C write at 9d98)

    9dd0: mvn  r2, #0               ; gain==0xFF path -> byte = 0xFF
    9dd4: mov  r3, r4                ; r3 = r4 (still 255 -- used for the cache-byte write at 9d98)
    9dd8: strb r2, [sp, #7]          ; data byte for I2C write = low byte of r2 = 0xFF
    9ddc: b    9d98
```

- `id` doubles as **both** the register/sub-address written **and** the
  selector passed to `get_data_addr(id)` to find the matching cache byte
  — i.e. each fader/balance/mixing channel has its own dedicated I2C
  sub-address, one per logical channel.
- Effective gain byte range: **`0x71`–`0xCF`**, with **`0xFF`** reserved
  as an explicit mute/off value for that channel.

## 12. `get_data_addr(uchar id)` @ `0x9bfc` (356 bytes)

A large binary-search / branch tree over `id` (values observed in the
comparisons: `2,3,5,6,43(0x2B),71(0x47),81(0x51),84(0x54),87(0x57)`, plus
many more branches later in the function) that returns
`object_base + <per-channel offset>` — i.e. a **channel-ID → cache-byte
lookup table** with roughly 40+ entries. Used exclusively by
`bd37033_set_fader_mixing_gain()` to locate each channel's cached
register byte before writing the same value out over I2C.

Example single case fully decoded:
```asm
    9c28: cmp r1, #0x54
    9c2c: bne 9d18
    9c30: add r0, r0, #72     ; id 0x54 -> object+0x48
    9c34: bx  lr
```

(The remaining ~40 branches follow the identical `cmp id,#N` /
`add r0,r0,#offset` / `bx lr` pattern and were not individually
transcribed — they represent the chip's per-channel fader/balance
register map, e.g. front-L/R, rear-L/R, center, subwoofer, etc., typical
of a 5.1-channel automotive/AV processor like the BD37033.)

## 16. Empirical Hardware Scan Results (2026-08-27)

To decisively resolve whether the BD37033's I2C control bus was active or inhibited by standby/power control on this physical board revision, a standalone hardware probe tool (`tools/bd37033-test`) was run directly on target hardware.

### Test Matrix & Live Console Output:
```text

    Address 0x40 (8-bit 0x80): No ACK
```

### Conclusions:
1. **Unpopulated / Inactive Control Bus**: Neither address `0x40` nor `0x41` acknowledges on any kernel bus or direct physical bit-banged pin pair (GPIO 9/121 or GPIO 3/2), regardless of whether GPIO 34 is driven LOW (`0`) or HIGH (`1`).
2. **Stock Alignment**: This proves why stock firmware shipped with `SoundType=0` (`MsnProductInfo.ini`).
3. **Active Audio Route**: The head unit routes PCM audio from the on-SoC Sigma-Delta DAC (`ark-sddac`) directly through the analog preamp to the power amplifier in bypass mode. All mixing, volume control, and audio quality tuning are governed in software via ALSA (`dmix`, `softvol`, and DSP filters).
