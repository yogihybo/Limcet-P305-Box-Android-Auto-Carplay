This board doesn't match the vendor schematic exactly

The reference design's camera decoder slot is ARK7116; this board actually populates RN6752 instead (confirmed by a live I2C probe finding dvr_rn6752@2c). ArkMicro's own kernel commit history notes RN6752 alone has a known random power‑on hang bug, and ARK7116(H) support was added specifically to pair alongside it as a fix — the two chips are closely related alternates, not unrelated options.

The Voice Processor doesn't seem to exist here

The schematic wires a dedicated SPI+I2C+I2S "Voice Processor" chip for hands‑free echo cancellation. This board's device tree has no SPI bus node at all, and no real boot log ever shows an SPI device probe. The real AEC path is software: the Bluetooth stack's HFP_NREC=3 setting, run over the mic's existing path through the SoC's own internal ADC (ahb:sdadc@0 ↔ i2s-adc) — not a separate chip.

Touch bypasses the MCU, contrary to an earlier theory

The schematic routes the touch panel's I2C straight to ARK1668, not through the MCU — independent, schematic‑level confirmation that touch activation on this unit is a Qt/QWS environment‑variable gate reading the controller directly, not an MCU‑handshake‑gated feature as an earlier project theory assumed. CBT16211A (a real, visible chip on the board) was once theorized as a touch‑bus switch tied to that handshake — that theory is still open, not settled.

WiFi isn't on the reference schematic at all

The vendor block diagram only shows a BT block with its own antenna and UART link (ttyHS1, confirmed). WiFi (RTL8821CU, appearing as a USB device in every boot log) isn't drawn anywhere on the original schematic — it's a real, working part of this board that simply wasn't part of the vendor's reference design, presumably added to support the wireless Android Auto/CarPlay handoff.

The MCU is a real, identified part

Visible directly on the board photo: an ARM‑marked STM32F105 QFP package sits where the schematic's generic "MCU" block is. This is the same chip libMcuCenter.so talks to over /dev/ttyHS0 using the McuType=6 ("BoxP300") protocol documented in MCU_ADAPTERS.md — steering‑wheel controls, ACC/ILL sensing, and backlight control all pass through it.
