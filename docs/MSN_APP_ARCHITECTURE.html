Built from real boot logs, D‑Bus service files, and binaries pulled from this project's firmware dump — not the vendor's own documentation, which doesn't exist for this board.

The plugin system is one process, not many

Everything in band 01 — libLauncher-Box.so, libSetting.so, libMsnCarAuto.so, and the rest — is dlopen()'d directly into MsnCoreApp's own address space at startup ([t] Load App Plugin N "path" in every boot log, in a fixed order). They share one Qt event loop and one DirectFB/QWS surface; switching "apps" on screen is a window swap inside a single PID, not a process switch.

Protocol work happens in separate daemons

The actual CarPlay/Android Auto/CarLife/MirrorLink protocol stacks are not in-process — each has its own binary (sink, carplay, msncarlife, mirrlink…) started on demand via D‑Bus service activation (MsnLink StartService: "com.arkmicro.auto"). The plugin only owns the UI chrome and talks to its daemon over a small AF_UNIX socket protocol (ArkUtils::open_local_socket, seen as sock = 3/4/9 in captured logs).

Two rendering paths, one app

start_msn launches Qt/QWS over plain linuxfb (writes straight to /dev/fb0, no GPU); a separate start_msn_directfb path runs the same binary over DirectFB, which goes through libGAL.so → the Vivante galcore.ko driver for GPU‑composited layers. Android Auto/CarPlay video always lands on the LCDC's own VIDEO_LAYER2 hardware plane either way — it's composited by the display controller, not drawn by Qt.

Vehicle I/O bypasses D‑Bus entirely

libMcuCenter.so and libCanBus.so don't go through the daemon/D‑Bus path at all — they talk directly over a UART (/dev/ttyHS0, the "MCU" — an on‑board microcontroller handling steering‑wheel controls, ACC/ILL sensing, and backlight) or the CAN transceiver. This is the same UART link this project's own mcu-handshake tool speaks to directly, bypassing MsnCoreApp altogether for testing.

Bluetooth is AT‑commands over serial, not D‑Bus

blueware is launched as a direct child process (start bt service:/usr/bin/blueware), not a D‑Bus service — libBlueTooth.so and libMsnCarAuto.so (for the AA WiFi/BT handoff) control it by writing AT commands over its own serial port and reading structured replies (rfcomm write: 00 09 00 04…), configured by /etc/blueware.properties (inc. HFP_NREC, the software echo‑cancellation toggle).

A lot of this image is dormant

usr/lib/ ships ~90 libraries — AirPlay, HiCar, DMSDP, five different Launcher-Box-* skins, CarLife variants — for the whole ArkMicro product family sharing one firmware build. Only what's reachable from a real boot log or an actually-present /usr/bin binary is drawn solid here; everything else (dimmed above) is present on disk but not exercised on this specific Prado unit.
